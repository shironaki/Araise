1. НАЗНАЧЕНИЕ ДОКУМЕНТА

Этот файл является постоянным паспортом проекта.

Он создан для того, чтобы состояние игры, принятые решения, игровые механики, техническая архитектура и текущие задачи не зависели от истории конкретного чата.

Если текущий диалог будет потерян, закончится контекст или разработка будет продолжена в новом чате, этот документ должен позволить восстановить состояние проекта.

Главное правило

Если решение существует только в переписке и не внесено в этот паспорт, оно не считается окончательно сохранённым решением проекта.

После существенного изменения игры паспорт необходимо обновлять.

2. ОСНОВНАЯ ИДЕЯ ПРОЕКТА

Мы создаём самостоятельную action-игру с элементами roguelike, исследованием комнат, сражениями, предметами, порталами, боссами, развитием персонажа и собственной системой теней.

Игра должна сочетать:

динамичное перемещение;
активный бой;
использование способностей;
HP и ману/энергию;
подбор предметов;
исследование комнат;
переходы через порталы;
последовательное прохождение зон;
элитных противников;
боссов;
развитие персонажа;
развитие и управление армией теней;
постоянную прогрессию между забегами;
сюжетное развитие.

В качестве ориентира по структуре игрового процесса используется подход мобильных action-roguelike игр, в частности система комнат, предметов, порталов, ресурсов и боевого перемещения, знакомая по Soul Knight.

Важно: Soul Knight используется только как ориентир по удобству и структуре игрового цикла. Наша игра не должна копировать его персонажей, мир, визуальный стиль, контент или конкретные механики.

3. ОСНОВНОЙ ПРИНЦИП РАЗРАБОТКИ

Мы не должны бесконечно исправлять отдельные симптомы.

Если несколько ошибок связаны одной системой, сначала проектируется сама система, после чего исправляются её проявления.

Пример:

Проблема с количеством теней не должна решаться отдельным исправлением интерфейса.

Сначала определяется единая модель:

максимальная вместимость;
фактическое количество теней;
активные тени;
потерянные тени;
восстановление;
получение новых теней.

После этого UI, способности и бой должны использовать одну и ту же систему данных.

5. СТРУКТУРА КОМНАТ

Комната является основной игровой единицей.

Типовая комната:

Игрок входит.
Начинается событие.
Появляются враги.
Игрок свободно перемещается.
Игрок сражается и использует способности.
Можно подбирать предметы.
После выполнения условия комнаты она считается очищенной.
Открывается дальнейший путь.
При необходимости появляется портал или другой переход.

Комнаты не должны превращаться в бесконечные арены без цели.

Каждая комната должна иметь понятную функцию:

обычный бой;
элитный бой;
награда;
магазин;
событие;
восстановление;
сюжет;
испытание;
босс.
6. ПОРТАЛЫ

Его назначение:

зафиксировать завершение текущего этапа и перевести игрока в следующую часть приключения.

В зависимости от дизайна порталы могут вести:

в следующую комнату;
в новую область;
к боссу;
в особую комнату;
к событию;
в секретную область.

При получении урона HP уменьшается.

При достижении нуля запускается предусмотренная системой смерти/поражения логика.

В дальнейшем необходимо определить:

максимальное HP;
восстановление;
источники лечения;
урон;
защиту;
временные щиты;
эффекты регенерации;
взаимодействие HP с предметами.
9. МАНА / ЭНЕРГИЯ

Мана/энергия используется для активных способностей.

10. МОБИЛЬНОЕ УПРАВЛЕНИЕ

Это один из текущих критических приоритетов.

Требование

Мобильная версия должна восприниматься как полноценная игра, а не как страница, которую пользователь случайно листает.

Необходимо
устранить случайное перелистывание экрана;
сделать игровую область полноценной зоной ввода;
обеспечить плавное движение;
предотвратить конфликт игрового управления с прокруткой страницы;
корректно работать с touch-событиями.
Главное правило

Движение персонажа не должно вызывать перелистывание/прокрутку игрового экрана.

11. ОДНОВРЕМЕННОЕ ДВИЖЕНИЕ И БОЙ

Текущее поведение является неправильным.

Сейчас:

Движение → остановка → атака/способность


Целевое поведение:

Движение
   +
Атака
   +
Способность


Игрок должен иметь возможность:

двигаться;
атаковать;
использовать силу;
управлять тенями;

одновременно.

Особенно важно это для мобильного управления.

12. СИСТЕМА ТЕНЕЙ

Система теней является одной из центральных уникальных механик игры.

Она должна быть отделена от обычного инвентаря.

Необходимо различать:

Вместимость хранилища

Максимальное количество теней, которое игрок способен содержать.

Например:

Хранилище: 2 / 8


означает:

максимальная вместимость: 8;
фактически имеется: 2.
Фактическое количество теней

Количество теней, которыми игрок реально располагает.

Это значение не должно автоматически равняться вместимости.

Активные тени

Количество теней, которые в данный момент находятся в бою/призваны.

Потерянные тени

Тени, которые погибли или были потеряны согласно правилам игры.

Необходимо определить, являются ли они:

временно недоступными;
окончательно потерянными;
восстанавливаемыми;
заменяемыми новыми тенями.
13. ХРАНИЛИЩЕ ТЕНЕЙ

Текущая проблема:

Хранилище было увеличено до 8, но фактически у игрока отображается только 2 тени.

Это означает, что вместимость и фактическое количество были смешаны либо одна из систем не синхронизирована.

Целевая модель:

shadowCapacity = 8
shadowCount = 2


UI должен отображать:

Тени: 2 / 8


а не трактовать увеличение вместимости как автоматическое получение новых теней.

14. ПОГИБШИЕ ТЕНИ

Текущая проблема:

После гибели теней их количество не восстанавливается в доступном хранилище.

Необходимо разработать полноценное правило восстановления.

Предварительное направление:

погибшая тень должна освобождать место;
игрок должен иметь возможность восполнить запас;
восстановление должно быть частью игровой экономики;
система не должна создавать бесконечные бесплатные тени;
интерфейс всегда должен показывать реальное состояние.

Окончательная механика будет определена отдельно.

15. КОМАНДИР ТЕНЕЙ

Командир теней — отдельная система развития.

Его улучшения должны иметь реальный эффект.

Текущая проблема:

Игрок получает/собирает улучшение Командира, но фактическое количество мест в хранилище не изменяется.

Целевая цепочка:

27. ТЕКУЩИЕ КРИТИЧЕСКИЕ ПРОБЛЕМЫ
BUG-001 — мобильное управление

Статус: ✅ Закрыто (01.09.2026)

Было: при движении на телефоне экран перелистывается; touch-action только на джойстике.

Стало: глобально `touch-action: manipulation`, `overscroll-behavior: none`; на мобильном body/арена `touch-action: none`, `height: 100dvh; overflow: hidden`, арена — flex-область без скролла.

Причина: конфликт игрового управления с прокруткой страницы.

BUG-002 — атака во время движения

Статус: ✅ Закрыто (01.09.2026)

Было: тач-кнопки на onclick — ненадёжно, конфликт с жестами.

Стало: тач-кнопки переведены на pointerdown + preventDefault; атака/способность работают во время движения.

Причина: click на тач-устройствах съедается жестом/скроллом.

BUG-003 — рассинхронизация хранилища теней

Статус: ✅ Закрыто (01.09.2026)

Было: вместимость зашита константой MAX_ARMY=8; UI показывал только фактическое количество; миграция могла «докидывать» теней.

Стало: единая модель — `capacity() = 8 + meta.commander` отдельно от `meta.shadows.length` (факт) и `S.army.length` (в бою); UI «2 / 8»; миграция ограничена вместимостью.

Причина: смешение вместимости и фактического количества.

BUG-004 — Командир теней

Статус: ✅ Закрыто (01.09.2026)

Было: улучшение КОМАНДИР ТЕНЕЙ пустое (() => {}), бонус в window.shadowArmyBonus нигде не читался.

Стало: улучшение увеличивает meta.commander → capacity() растёт → сохраняется в localStorage → UI обновляется.

Причина: улучшение не было связано с игровым параметром.

BUG-005 — устаревший путь в launch.json

DESIGN-001 — бесконечная рутина волн

Статус: ✅ Реализован MVP (01.09.2026)

Реализовано:

1. Типы комнат: fight (4 + portal/2 врагов), elite (2 + portal/2 сильных с множителем HP), reward (лечение + выбор усиления), portal (переход-оверлей), boss (Хранитель Врат).
2. Цепочка зоны: fight → fight → elite → reward → fight → elite → portal → boss → награда → новая зона.
3. Замена wave()/goal на startRoom(); условие очистки — «врагов нет → комната очищена».
4. Оверлей «КОМНАТА ОЧИЩЕНА» с кнопкой «ДАЛЬШЕ» (переход через #next → nextRoom()).
5. Зона = meta.portal; названия зон из portalNames.
6. UI: objective показывает «ЗОНА N · КОМНАТА · врагов: N».
7. Элита: spawn(type, boss, elite) — множитель HP 2.1 + portal*0.15.
8. Босс завершает зону → finish(true) → meta.portal++ → следующая зона.

Проверено: smoke-тест, 21 проверка, все зелёные (бой → очистка → next → вторая комната → элита).

Открыто: портал-объект на канвасе (вместо оверлея), магазин, события, восстановление, испытания, сюжетные комнаты — следующие типы после MVP.

Решение DESIGN-001 (MVP комнат и зон):

Типы комнат (5 работающих):
- fight — обычный бой: одна партия врагов (4 + portal/2), без бесконечных волн

35. ГЛАВНОЕ ПРАВИЛО ПРОЕКТА

Мы строим не набор отдельных механик.

Мы строим единую игру, в которой:

управление → бой → ресурсы → предметы → тени → комнаты → порталы → зоны → боссы → прогрессия → сюжет

связаны между собой одной системой.

Каждая новая механика должна усиливать общий игровой цикл, а не существовать отдельно от него.
